# packages/db

Drizzle schema, migrations, RLS policies, the database roles and the tenant context (ADR 0004, ADR 0016, ADR 0020). PostgreSQL 17, node-postgres driver, snake_case columns from camelCase properties. Copied from Vertex Shifa's `packages/db` and adapted.

## Layout
- `src/schema/<module>.ts`: one file per owning module, exported from `schema/index.ts`. Patterns to copy: `schema/tenancy.ts` (`branches`: a tenant business table, parent of composite keys; `branch_hours`: a replaceable set; `tenants`, `tenant_slugs`: platform tables), `schema/files.ts` (a tenant table with `bytea`), `schema/areas.ts` (platform reference data), `schema/audit.ts` (append-only, tenant and platform), `schema/events.ts` (a tenant work queue), `schema/identity.ts` and `schema/access.ts` (spec S02: accounts and the console's platform tables, tenant memberships, PINs, PCs and sessions; `used_tokens`, append-only). A platform table never has a column named `tenant_id` (the convention test reads that as tenant scope): it names the tenant it points at, as `tenant_slugs.subject_tenant_id`.
- `src/schema/columns.ts`: the shared column helpers (`id`, `idIsUuidV7`, `tenantId`, `timestamptz`, `createdAt`, `updatedAt`, `archivedAt`). Name a column explicitly when the snake_case casing would split it (`integer('latitude_e7')`, not `latitude_e_7`).
- `src/schema/registry.ts`: every table with its owning module, scope (`tenant`, `platform`) and kind (`business`, `append-only`, `queue`, `replaceable`: rows replaced as a set, the only kind the app role deletes from).
- `src/operators.ts`: drizzle's query operators re-exported for the worker, whose own drizzle-orm resolves to another copy (pg-boss's `@opentelemetry/api` peer).
- `src/client.ts`: `createDatabase(url)`, a pool with `DATABASE_DEADLINES` (connect 5 s; per session `statement_timeout` 10 s, `lock_timeout` 5 s, `idle_in_transaction_session_timeout` 30 s, sent at connection start so they bind every role and need no role grant; a job that needs longer sets `SET LOCAL statement_timeout` in its transaction) and an `error` listener on every client, so a connection lost while idle or inside a transaction is logged through `describeForLog`, fails only that transaction and is replaced instead of ending the process (`test/pool.test.ts`). `src/tenant-context.ts`: `withTenant(db, tenantId, work)` and `enterTenant(tx, tenantId)`. `src/describe-for-log.ts`: `describeForLog(error)`, what an unexpected error may write to the log (no values, ADR 0016), used by the apps.
- `migrations/`: generated SQL plus custom migrations (RLS, triggers, grants, backfills, reference seeds with fixed UUIDv7 ids). The pattern for a custom migration: `0001_tenant-isolation-and-roles.sql`. Never read or edit `migrations/meta/`.
- `scripts/setup-local.ts`: the local PostgreSQL setup (`pnpm db:setup-local`).
- `src/testing.ts` (`@vertex-food/db/testing`): `createTestDatabase()`, a fresh migrated database for one test run, used by this package's and the apps' test global setups. It first drops the test databases that killed runs left behind (older than 6 hours, nobody connected; `test/testing.test.ts`).
- `test/`: run against a fresh database per run (`test/global-setup.ts`). `conventions.test.ts` reads the rules below from the migrated database; `tenant-isolation.test.ts`, `append-only.test.ts`, `platform-jobs.test.ts` and `roles.test.ts` try them as each role.

## Roles
- `food_owner` runs migrations and owns every table, function and schema. It cannot bypass RLS either: with forced RLS it sees tenant rows only inside `withTenant`. Locally it may create databases, for the test runs.
- `food_app` is what the apps connect as: no `BYPASSRLS`, only the privileges each table's custom migration grants. It cannot turn row security off (the query then fails), change a policy, trigger or function, empty a table, create objects or switch role (`roles.test.ts`).
- `food_jobs` is the audited platform-jobs role (ADR 0004) for the worker's cross-tenant jobs. It has no `BYPASSRLS`: it reaches across tenants only through policies of its own (`TO food_jobs`) on the tables granted to it, so a stray grant still shows no tenant rows. Today: `SELECT` and `UPDATE (dispatched_at, updated_at)` on `outbox_events`, to read and claim events; `SELECT` and `UPDATE` of the status columns on `tenants` (platform data, no RLS) for `tenancy/apply-scheduled-status`; `INSERT` on `audit_entries` and `outbox_events` for that job's entry and event, which it writes inside `withTenant`, so `tenant_isolation` bounds them to the tenant; no read of the audit log. Audited by `log_statement = 'all'` on the role, so every statement it runs is in the server log, and `log_parameter_max_length = 0`, so the values it passes (outbox payloads handed to pg-boss) are not; only a superuser can change either. Its statement texts carry ids and timestamps only. A new grant to it is listed in `JOBS_ACCESS` in `conventions.test.ts`, which fails on anything else.
- `food_queue` is the queue role pg-boss runs as (`apps/worker`), never `food_jobs`. It has no privilege on any `public` table; it holds `USAGE, CREATE` on schema `pgboss`, where pg-boss installs, migrates and owns its tables at start. The jobs role has `USAGE` on that schema; the worker grants it the pg-boss tables of its hand-off.
- `food_sync` is the sync service's replication role (ADR 0022, Vertex Shifa ADR 0021): `REPLICATION` and `BYPASSRLS`, because PowerSync's snapshot reads would otherwise return no rows, and the only role that bypasses RLS. Through SQL it writes nothing and reads only the tables a migration publishes to it: the migration creates the `powersync` publication with an explicit table list (never `FOR ALL TABLES`) and grants `SELECT` on each, and `SYNC_ACCESS` in `conventions.test.ts` lists them, failing on any other grant or published table. Empty until S04. Isolation of what it streams to devices rests on the sync rules' `tenant_id` and branch filters.
- What no grant limits: `REPLICATION` lets the role create logical slots and decode every change in the database with any output plugin the server has (`test_decoding` ships with PostgreSQL), and slots it leaves behind hold WAL until the disk fills. So the server, set up by `deploy/`, must: carry no output plugin but the built-in `pgoutput` (remove `test_decoding` and `wal2json`); set `max_slot_wal_keep_size`; alert on any slot that is not PowerSync's `pgoutput` slot; give the role no `replication` entry in `pg_hba.conf` (that would allow a physical copy of everything), only the application database. The owner's decision on this residual risk is open question Q20; until then the deploy skeleton follows its recommendation.
- All five exist before the first migration (cluster-wide, created by `pnpm db:setup-local`; on servers by `deploy/`, which must also set the jobs role's `log_statement` and `log_parameter_max_length` and `wal_level = logical` for the sync service). No role is a member of another.

## Rules
- Changes go through `/db-migration`. Never `drizzle-kit push`, never edit a generated migration; commit the schema and its migration together; expand, then contract.
- Every table: in the `public` schema (pg-boss's tables in `pgboss` are the one exception, left out of the convention test's table checks and pinned by the worker's tests); UUIDv7 `id` with `idIsUuidV7`, `created_at`; a `tableRegistry` entry; no `real`, `double precision`, `money` or zoneless `timestamp` column; every foreign key indexed. The app role never gets `TRUNCATE` (it ignores RLS), `TRIGGER` or `REFERENCES`, nor `DELETE` on business tables (archive instead). No function is `SECURITY DEFINER`.
- Money columns (ADR 0014): `bigint({ mode: 'number' })` minor units beside a `currency` text column with a check on the codes of `currencies` in `@vertex-food/contracts`; an exchange rate as `numeric`, which Drizzle reads as the decimal string `exchangeRateSchema` takes. Never a float.
- Tenant tables (scope `tenant`): `tenant_id` not null, secondary indexes start with it (except a partial index for the jobs role's cross-tenant claim, listed in `CROSS_TENANT_INDEXES` in `conventions.test.ts`: today `outbox_events_pending_idx`); foreign keys between tenant tables are composite, `(tenant_id, x_id) → (tenant_id, id)` with `unique (tenant_id, id)` on the parent, because PostgreSQL checks foreign keys without RLS and a plain key would accept another tenant's id; the custom migration enables and forces RLS and creates the one permissive policy `tenant_isolation` with `USING` and `WITH CHECK (tenant_id = current_tenant_id())`, revokes `PUBLIC` and grants the app role what it needs.
- `current_tenant_id()` reads only the transaction setting: no fallback, no `SECURITY DEFINER`; the convention test pins its body. Never disable a `refuse_change` trigger.
- Tenant data is read and written only inside `withTenant`, with the tenant from the authenticated session or device token, never from client input. The one way to reach a second tenant in the same transaction is `enterTenant(tx, tenantId)`, for account-level changes across the tenants of the account's own links (ADR 0005). Outside it the app role sees no tenant rows and cannot insert any.
- Append-only tables: no `updated_at` or `archived_at`; triggers with `refuse_change()` refuse `UPDATE`, `DELETE` and `TRUNCATE` for every role; the app role gets `SELECT, INSERT` only.
- `outbox_events`: the API adds events, always pending (trigger `outbox_events_pending_on_insert`), in its tenant's transaction; the only change allowed afterwards, for every role, is the claim that sets `dispatched_at` once (trigger `outbox_events_claim_only`); no role deletes or empties it (`refuse_change` triggers), so no event is dropped silently.
- Audit entries and outbox payloads hold ids and codes, never a customer's phone or address or a driver's location (ADR 0016).
- The database holds what the services guarantee, so another writer cannot store what the API would refuse: checks repeat the contracts' shapes (Latin names, phone JSON, distinct currencies, whole-minute times, exception periods, through `jsonb_path_exists` for JSON), and counts or "exactly one" rules are unique partial indexes or triggers (`0005_tenancy-audit-guards.sql`: one primary slug, checked at commit; two periods per weekday). A check on a function that can answer NULL says `is true` (`idIsUuidV7`).

## Local database
1. PostgreSQL 17 running locally (the Windows installer, or `docker run -d -p 127.0.0.1:5432:5432 -e POSTGRES_PASSWORD=… postgres:17`).
2. Copy `.env.example` to `.env` at the repository root and set the six URLs: a superuser of your server for `DATABASE_ADMIN_URL`, passwords of your choice for the five roles.
3. `pnpm db:setup-local` (creates or updates the roles and the `vertex_food` database; never drops anything), then `pnpm db:migrate`.

The tests need the owner, app, jobs, queue and sync URLs: each run creates `food_test_<time>_<random>`, migrates it and drops it; a run killed before that leaves its database, which a run 6 hours later drops. Turborepo passes only the URLs listed in `passThroughEnv` of the `test` task in `turbo.json`.

Run: `pnpm --filter @vertex-food/db test`.
