# packages/contracts

Zod schemas and pure rules shared by every app and client (ADR 0002, ADR 0020). No I/O, no Node APIs (`tsconfig.json` loads no Node types), fully unit-tested. Copied from Vertex Shifa's `packages/contracts` and adapted.

## Layout
- `src/<module>.ts` with `src/<module>.test.ts` next to it; `src/index.ts` re-exports every file.
- `errors.ts`: stable error codes with their HTTP status, `errorResponseSchema`, `DomainError`. The pattern to copy for a schema: `errorResponseSchema`; for a module with rules: `money.ts`.
- `money.ts`: currencies (USD, TRY, SYP with their exponents, published as `x-exponents` on `CurrencyCode`), `moneySchema`, `exchangeRateSchema`, arithmetic, conversion, parsing and formatting (ADR 0014).
- `health-check.ts`: `healthCheckSchema` (`GET /api/health`: up and reaching the database) and `livenessSchema` (`GET /health` of the worker and the gateway).
- `primitives.ts`: `idSchema` (UUIDv7), `instantSchema` (ISO 8601 UTC), `coordinatesSchema` (degrees × 10⁷), `listQuerySchema(sortKeys)` and `pageSchema(item)` for every list endpoint.
- `json-schema.ts`: `contractJsonSchemas()`, every schema with an id as JSON Schema (draft 2020-12), for clients that do not run TypeScript (a Flutter or native app) and for the API's OpenAPI document.
- `tenancy.ts` (spec S01, **the pattern to copy for a module with a state table and rules**): the tenant status table with `planTenantStatusChange`, `effectiveStatus` and `nextBusinessDayEnd`; slugs; weekly hours and exceptions (`validateWeeklyHours`, `businessDateOf`, `isBranchOpenAt`); sales channels (`salesChannelSchema`: how a branch sells, the food domain's order types) and charge lines in basis points; `onboardingCompleteness`; the restaurant and console schemas. `time.ts`: wall-clock times and dates in `Asia/Damascus` through `Intl` (no offset written in code). `areas.ts`, `files.ts` (`imageUploadRules`), `maps.ts` (map-link parsing without `URL`), `phone.ts` (Syrian and Turkish E.164, from Vertex Shifa), `access.ts` (permissions), `identity.ts`, `staff.ts`, `console-identity.ts` (spec S02), `proof-of-work.ts` (the client's solver, pure JavaScript with `@noble/hashes`), `audit.ts` (audit actions), `events.ts` (the outbox event catalog). `messaging.ts` (spec S03, from Vertex Shifa): WhatsApp session states and transitions, message kinds and forward-only statuses, `whatsappPolicy` (ADR 0034's limits), `messageTemplates` (a key, its kind, a strict parameter schema and, for `notification`, its deadline; the text is in `packages/i18n`), `sendBudget` and `chooseWhatsAppNumber`, the keyword matcher, the console and delivery-route shapes. `sync.ts` (spec S04): the signed command envelope, outcomes and reason codes, upload, heartbeat, number-block, certificate, quarantine, attention and hub-role shapes; protocol and app versions, the clock rules (offset, effective time, `clockSuspectReasons`, `inactiveMemberDecision`), the block layout and provisional labels, `branchConnectivity` with ADR 0035's thresholds. `hub.ts`: the hub's LAN API (pairing window and QR, hello, member sessions, command answers, the live snapshot) and `hubPolicy`. `commercial.ts` (spec S05, platform: keys are plain strings): `defineFeature`, `defineLimit`, `assembleFeatureCatalog` and the platform's entries; packages, templates, term values and drafts, amendments with their state table (`nextAmendmentStatus`) and four eyes (`assertNotAuthor`), `planAmendment` (rules 4–7: no past date, endings of open terms, removals pushed to the next business day end by `removalTakesEffectAt`, no overlap in a slot, dependencies at every instant), `termsInForce`, overrides with `planOverride` and `planRevocation`, the console views. `restaurant-features.ts` (food) and `marketplace-features.ts` (product) declare their layer's features; `feature-catalog.ts` (product layer) assembles `featureCatalog`, `featureKeySchema` and `limitKeySchema`. `entitlements.ts`: `resolveEntitlements` (rule 15, with `until` and `validUntil`), the branch copy and `isBranchFeatureEntitled` (rule 24), the 7-day lease, `assertWithinLimit`, the reading views. `commercial-money.ts`: `commissionFor`, `deliveryFeeShareFor`, `recurringChargeFor` (rules 29–33).

## Rules
- Schemas `<thing>Schema`, types `Thing = z.infer<…>`, inputs `create<Thing>Schema`; every schema the API exposes has a stable `.meta({ id })` and is added to the list in `json-schema.test.ts`.
- Every schema converts to JSON Schema: no `transform`, `custom` or other shape JSON Schema cannot hold in a schema with an id (the test fails on one). Rules beyond the shape (`refine`) run in TypeScript clients only, so the server validates them again.
- Error codes are upper snake case and never renamed or removed: offline restaurant devices and installed apps on older versions still read them. A new code gets its HTTP status in `errorStatus`, a line in the list in `errors.test.ts` and its Arabic text in `packages/i18n`. Each spec adds the codes of its rules (`ITEM_SOLD_OUT`, `BRANCH_CLOSED`, `OUTSIDE_DELIVERY_ZONE`, `BELOW_MINIMUM`…).
- Money is whole minor units in a JavaScript safe integer with a currency (stored as `bigint`). Never floats, never `Number` division on amounts: use the functions in `money.ts`, which refuse what they cannot represent instead of rounding. Conversion rounds half away from zero; the caller stores the rate it used. The SYP exponent follows open question Q11; changing it once amounts are stored also needs a data migration of every stored SYP amount.
- Ids on the wire are UUIDv7 (`idSchema`); instants are UTC with `Z` (`instantSchema`); coordinates are integers × 10⁷, never floats.
- A refusal by a business rule throws `DomainError` with a code; input that fails a schema throws Zod's error.
- Messages and payloads never carry a customer's phone or address or a driver's location into logs (ADR 0016).
