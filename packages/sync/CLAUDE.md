# packages/sync

The sync foundation of the restaurant (spec S04, ADR 0008, 0022, 0035): the command registry, the canonical JSON every hash and signature is made over, envelope signing and checking, the sync service's stream definitions, the hub protocol (`src/hub/`: journal, checked mirroring, heartbeats, epochs, promotion, rejoin, forwarding, catch-up, pairing and PIN sessions) and the client outbox (`src/client/`), pure logic behind storage, clock and transport ports. The command envelope's shape and the hub's LAN API are schemas in `packages/contracts` (`sync.ts`, `hub.ts`); the protocol between the hub-capable PCs (`/peer/*`) is internal, in `src/hub/peer.ts`. S04's PR 5 implements the ports on the encrypted local database, the HTTPS LAN server and the device keys.

## Layout
- `src/canonical.ts`: `canonicalJson` (keys sorted by UTF-16 code units, no whitespace, safe integers only, undefined keys left out; anything else throws `CanonicalJsonError`), `sha256Hex`, `commandPayloadHash` (SHA-256 of `{ payload, resolved }`). Pinned by fixed vectors in `canonical.test.ts`: changing the output invalidates every signature an installed PC made.
- `src/envelope.ts`: `envelopeSigningMessage` (the tag `vertex-food/command/v1` and the canonical envelope without `signature`), `signEnvelope`, `checkEnvelope` (shape, hash, signature; `payload_invalid` or `signature_invalid`). Signing and verifying are ports (`SignMessage`, `VerifyMessage`).
- `src/node.ts` (`@vertex-food/sync/node`): `ed25519Signer` (a PKCS #8 device key) and `ed25519Verifier` (a raw public key, as `devices.public_key` holds it), with `node:crypto`. Only Node runtimes import it.
- `src/registry.ts`: `defineCommand`, `createCommandRegistry`, `CommandDefinition` (name, version, payload and resolved schemas, access, `resolve` on the hub, `describe` for needs attention, optional `alreadyApplied`), `ResolveContext`. The server's `execute` lives in the API module that owns each command.
- `src/commands/<module>.ts`: one file per owning module; `commands/index.ts` builds `commandRegistry`. S04: `sync.network_check` (`hub.manage`) and `audit.record_local_events` (the PC itself, `localEventActions`). `describe` answers an i18n key of the `sync` namespace (`commands.<module>.<action>`) and its parameters, never customer data.
- `src/hub/` (adapted from Spike A's tested `spikes/restaurant-hub/pc/pc.mjs`): `hub.ts` is `BranchHub`, one per hub-capable PC: `start()` (asks the peers before serving, takes back what its standby holds, rule 23), `tick()` (the runtime calls it every `hubPolicy.heartbeatMs`: heartbeats on the hub, the 3 s watchdog on the standby; no timer lives in this package), `submit(command, source)` (duplicate by id; registry, payload, local access; a re-sent version applied as signed when it passes the re-checks; resolve, mirror first with 0.8 s, then one transaction; `ok`/`duplicate`/`refused`/`not_hub`), `promoteManually`, `retire`, `pruneJournal`, `rejoinAfterServerSync`, `hello`, `liveSnapshot`, `onChange`, and the `/peer/*` handlers. `ports.ts`: `HubStore` and `HubTransaction` (journal, hub state, local blocks, pairings, sessions, lockouts, local events, upload queue and optimistic rows in one transaction), `HubClock`, `HubRandom`, `MemberDirectory`, `BranchData`. `journal.ts`: entries (commands with their signed envelope and the number used; local `hub.pairing`, `hub.session`, `hub.pin_disabled`), compared by id and hash. `peer.ts`: the `/peer/*` schemas, `PeerLink`, the tie-break `outranks`. `access.ts`: `checkLocalAccess` (rules 5, 6, 35, 36). `numbering.ts`: `HubResolveContext` (a numbering definition types its `resolve` context with it and calls `takeNumber`), provisional labels. `pairing.ts`: `PairingDesk` (window, codes, delays, single use, revocation, expiry, PIN sessions and lockout).
- `src/client/`: `HubClient` (discovery by highest epoch, the outbox state machine over an `OutboxStore`, re-sent versions, "sending" counts) and `chooseHub`; hub client pages keep the outbox in IndexedDB, client PCs in `local_outbox`.
- `src/test-support/` (not built): the ports in memory (`MemoryHubStore` with power cuts, `MemoryLan` with cuts and dropped calls, a manual clock) and `TestBranch` (two PCs, phones, client PCs, order-like test commands that number, price and write rows). `src/hub/scenarios.test.ts` is Spike A's suite on them; PR 5 runs it again on the real ports.
- `powersync/`: the sync service, PowerSync Open Edition pinned at `1.27.0`: `service.yaml` (only `PS_*` variables), `sync-config.yaml` (the streams: named columns of published tables, every query filtered by the token's `tenant_id` and `branch_id`), `docker-compose.yaml` for development (`pnpm sync:up`, `pnpm sync:down`). `src/stream-conventions.test.ts` checks each query against the tables the migrations publish (`turbo.json` adds `packages/db/migrations` to this package's test inputs).

## Rules
- Pure TypeScript: no Node built-in outside `src/node.ts` (`registry.test.ts` checks it), because hub client pages load this package in a browser.
- The hub is the only writer of branch commands: every journal and hub-state change runs under its `WriterLock`, and every write is one `HubStore` transaction. A peer handler that can be called while the caller holds its own lock never waits on the lock when it can answer at once (a hub answering a mirror, a rejoining standby).
- An envelope is signed once by the PC that resolves it and never changed: a forwarded or re-sent entry keeps its envelope (and its `hubEpoch`, `hubSeq`) and only gets a new place in the journal; a hub that cannot verify it resolves the command again under its own signature (rule 26). A command-specific re-check of a resolved version (prices in force, an order's lines) goes into `BranchHubPorts.rechecks` by command name.
- Every command a hub runs takes the hub's clock as its `deviceTime`, with the hub's offset and highest seen time (PR 1's review): hub clients and client PCs measure no offset. A hub client never sends a `device` actor; only a PC by mutual TLS does.
- A command is never changed once a release sends it: a new payload is a new version, and the old version stays registered until no supported app sends it (ADR 0035's previous protocol).
- Payloads and resolved versions may hold customer data in later specs: never log them, put them in an error, or let `describe` return them (ADR 0006, 0016).
- A new published table: the migration publishes and grants it (`packages/db`, `SYNC_ACCESS`), and a query here names its columns and filters it by tenant and branch. The sync service reads whole rows, so a column devices must not get lives in an unpublished table.

## The sync service locally
1. PostgreSQL with `wal_level = logical` (as a superuser: `ALTER SYSTEM SET wal_level = logical;`, then restart the server); `pnpm db:setup-local` with `POWERSYNC_STORAGE_URI` set creates the bucket storage: the role `food_sync_storage`, owning `vertex_food_powersync`, with no access to the development database. The sync service gets only the sync role's and this role's credentials, never another role's (ADR 0035).
2. Docker Desktop; the `POWERSYNC_*` keys of `.env.example` in `.env`.
3. `pnpm sync:up` (the API's JWKS on port 3100 for device tokens), `pnpm sync:down` to stop. S04's PR 5 runs the sync scenarios against it.

Run: `pnpm --filter @vertex-food/sync test`.
