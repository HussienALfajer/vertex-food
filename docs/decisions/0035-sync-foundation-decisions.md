# 0035 — Sync foundation: signed commands, two hub PCs, number blocks, versioned protocol, guarded replication

Status: Accepted (owner, 2026-10-28) · Date: 2026-10-28 · Amends [0008](0008-offline-first-restaurant-and-lan-hub.md) and [0022](0022-branch-hub-confirmed-by-spike-a.md); touches [0030](0030-offline-weak-connection-and-offline-redemption.md) (thresholds) · Spec: [S04](../specs/S04-sync-foundation-and-restaurant-hub.md)

## Context
ADR 0022 confirmed the branch hub after Spike A and left several items to S04: the sync service's replication role (Q20), how many PCs may be hub-capable, the number range layout and the days reserved ahead, the peer credential and the signature on re-sent versions, how a browser on a phone gets the branch CA (Q17 stays open for S11 and S12), the client and protocol versions (VER-01 in the 2026-10-20 audit), the clock-skew limit S02 refers to, and ADR 0030's connectivity thresholds. The owner settled the business side of each in the S04 interview (2026-10-28).

## Decision
- **Replication role (Q20, owner 2026-10-28):** accepted with server-side guards set by `deploy/`: only the built-in `pgoutput` plugin installed on the server (no `test_decoding`, no `wal2json`), `max_slot_wal_keep_size` set, an alert on any replication slot other than PowerSync's, and the role's password only in the sync service's environment. Streams select only the columns a device needs, filtered by the token's `tenant_id` and `branch_id`; a convention test fails any stream without both filters.
- **Two hub-capable PCs per branch (owner):** one configured hub and one configured standby, set online by an owner or manager (`hub.manage`). The first two PCs registered to a branch take these roles by default. Every other PC of the branch is a **client PC**: it reads its own synced database, sends its commands to the active hub over the LAN like a waiter phone, and, when both hub-capable PCs are down, keeps its commands as "sending" until one returns (owner). Making the standby the hub is a manual promotion by PIN (`hub.manage`), offline too; it uses the epoch rules of ADR 0022.
- **Number blocks (owner):** per branch, per series (`order` first) and per business day, the server hands out blocks of numbers: block 1 is 1–4999, block 2 is 5001–9999, block 3 is 10001–14999, and so on. The configured hub takes the lowest free block and the standby the next, so a day normally runs 1, 2, 3… and a jump to 5001 shows that the standby numbered. Blocks are reserved for the current and the next 6 business days, are never reused, and stay with the PC that holds them. The business day is the branch's existing `business_day_ends_at` (S01, default 04:00), which the owner chose over midnight or the end-of-day closure. A PC that uses its whole block numbers further orders from a provisional label, and the server assigns their number on sync.
- **Signed commands:** the executing PC signs every resolved command (envelope, payload and resolved version) with its Ed25519 device key (S02). The server verifies the signature against the device's public key; a hub that receives a re-sent version verifies the original executor's signature with the branch PCs' public keys it holds, then applies its own checks of ADR 0022. This replaces "(not tested) the executing PC also signs the resolved version with its peer credential".
- **Peer credential:** hub-capable and client PCs authenticate each other by mutual TLS with their PC certificates signed by the branch CA, each naming its device id; a peer must be an active PC of the branch in the synced device list. The spike's shared branch secret is dropped. The platform creates the branch CA at the first PC registration of the branch, keeps its key sealed (`packages/crypto`), and issues PC certificates online for the PC's private LAN addresses.
- **CA for browsers (owner, Q17 open):** while a manager has pairing open, the hub also answers plain HTTP on a second port with one file only, the branch CA certificate, and shows its SHA-256 fingerprint next to the download QR so the installer compares it on the phone. Nothing else is served over plain HTTP; ADR 0022's "no plain HTTP on the LAN" holds for every page and command. Whether pilot phones need a small Android app instead stays Q17.
- **Pairing (owner):** a pairing lasts until a manager revokes it or the paired device is unused for 30 days. A waiter phone still needs the waiter's PIN for each session; a station (kitchen display) acts as the station.
- **Protocol and app versions (VER-01, owner):** every device request carries the app version and the sync protocol version. The server accepts the current and the previous protocol version. Below the platform's minimum app version a PC still uploads its pending commands, then shows "update required" and keeps working locally; it gets no new sync data until it updates. Updates download in the background and install only at an app restart with an empty upload queue and an uploaded hub journal; nothing forces a restart during service. Hub, standby and client PCs accept peers of the current and the previous LAN protocol version; hub client pages are served by the hub and reload when its version changes.
- **Clock skew (owner):** 10 minutes. Each command carries the device time and the PC's last measured offset from server time. A command whose corrected time is uncertain by more than 10 minutes, or that lies more than 10 minutes in the future, is flagged `clock_suspect`; where the time decides access (a member deactivated during a cut, S02 rule 33), a suspect or borderline command goes to the quarantine.
- **Connectivity thresholds (owner, ADR 0030):** each hub-capable PC sends a heartbeat every 15 s. A branch is `weak` after 45 s without a heartbeat or when 3 of the last 5 round trips exceed 3 s, `offline` after 3 minutes without a heartbeat, and `online` again after 4 healthy heartbeats in a row. The branch takes the best state among its hub-capable PCs.
- **Needs attention (owner):** an `adjusted` or `rejected` outcome, a replay with a different payload, a taken number, or a command from a clock-suspect PC opens an attention item. The member who made the command sees it, and the branch's owners and managers see all of them; an owner or manager closes one with a written reason, which is audited.
- **Access at the command's time:** S02's promise that a command is checked against the permissions the member held when it was made needs history, so every access change appends a membership access snapshot; the server checks a command against the snapshot in force at its corrected time.

## Consequences
- `packages/sync` holds the command envelope, the registry, the hub protocol and the outbox; the server's executor lives in the API's `platform/sync` module. The spike's scenarios become the sync test suite, plus signature, block, version, skew and quarantine cases.
- One more TLS port and one plain-HTTP port in the Windows firewall rule of the installer; the plain-HTTP port listens only while pairing is open.
- A branch with three or more PCs depends on its two hub-capable PCs for LAN work; the third PC is never a hub in V1.
- More than 4999 orders on one PC in one business day get provisional labels until sync.
- `docs/open-questions.md` Q20 is resolved; Q17 stays open for S11 and S12; the real power-cut test on pilot hardware (Q8) is S04's acceptance after the merge.
