# 0034 — Platform messaging: two numbers, a database send queue, limits from sent messages

Status: Accepted (owner, 2026-10-28) · Date: 2026-10-28 · Amends [0012](0012-messaging-whatsapp-and-push.md) · Spec: [S03](../specs/S03-whatsapp-gateway-and-otp.md)

## Context
ADR 0012 copies Vertex Shifa's gateway and says its spike findings apply without a new spike, but leaves open how many platform numbers Vertex runs (Q4), how a message made in the API or the worker reaches the gateway (a separate process), and the tables. S02 sends OTPs synchronously through an `OtpSender` port, so the code is never stored in clear, and answers `OTP_DELIVERY_UNAVAILABLE` when sending is impossible. The gateway paces sends per number, so a synchronous call into it would make a sign-in wait for another person's gap. Vertex Shifa settled the same questions in its ADRs 0022 (Spike B, run from Azaz on 2026-10-09) and 0026.

## Decision
- **Numbers (Q4, owner 2026-10-28):** two platform numbers at launch, one Syrian and one Turkish SIM, separate from Vertex Shifa's, phones kept by the owner, linked by admins from a console screen by QR. Every message may go from any healthy number, preferring the number that already knows the recipient, so both stay warm and either can carry the whole load.
- **Baileys, as Vertex Shifa's Spike B found:** pinned to an exact v7 version with the `WEB_BROWSER` sub-platform; "linked" means an open connection with `creds.me` set (not `creds.registered`); `515` reconnects once at once, `401` needs a re-link, `403` is a ban, `440` closes the connection and never reconnects; one session per number under a database lease (30 s, renewed every 10 s); receipts only move a message forward; sent text kept sealed one hour for retry requests; both `notify` and `append` incoming messages, de-duplicated; history sync and presence off; upgrades tested on a test number first. Starting limits per number: 6–12 s between sends, 60 an hour, 30/75/150/300 a day by warm-up age (days 1, 4, 8, 22), first contacts at most half the daily cap; per recipient, except OTPs, 1 a minute, 5 an hour, 10 a day. Raised only after weeks without bans, failed sends or missing receipts.
- **Send queue in PostgreSQL:** every outgoing WhatsApp message is a row of `whatsapp_messages`, recipient sealed and hashed, template parameters sealed. The API (OTPs), the gateway (alerts, replies) and, from S14, the worker (notifications) insert rows through one writer in `packages/db`; the gateway claims them by priority with `FOR UPDATE SKIP LOCKED`, woken by `NOTIFY`, renders the text and sends. No HTTP between the API and the gateway; the gateway does not run pg-boss. The API checks synchronously that a healthy number could send now, so `OTP_DELIVERY_UNAVAILABLE` keeps its meaning.
- **Templates are code:** a key, a kind and a parameter schema in `packages/contracts`, the Arabic text in `packages/i18n`. Later specs add transactional templates (order status, the customer link) and their triggers; no template table and no console editing in V1.
- **Limits from sent messages:** counted over `whatsapp_messages.sent_at` in rolling windows with the database clock. The `send_counters` table in the architecture's module map is not built; Baileys' LID–phone pairs stay in its sealed credential store.
- **Opt-out** («إيقاف» / «تشغيل», owner 2026-10-28) stops every WhatsApp message from platform numbers except the OTPs the person requests: order-status and link messages, alerts and auto-replies; push is not affected. Strangers' messages are dropped unstored; known recipients get one auto-reply a day pointing to the restaurant or in-app support.
- **Alerts** (owner, 2026-10-28): a failing number, or none healthy, shows a console banner and sends a WhatsApp alert from a healthy number to every active platform user who manages messaging.
- **Shared crypto** (owner, 2026-10-28): the keyed hash and secret box of S02 move from `apps/api` to `packages/crypto`, used by the API, the worker and the gateway, with messaging keys of their own (`MESSAGING_ENCRYPTION_KEY`, `MESSAGING_HASH_KEY`).

## Consequences
- OTP delivery is asynchronous after the availability check; the restaurant app reads the delivery status of a new-device OTP, and a failed delivery can be resent at once.
- Throughput is bounded by the pacing: about 10–20 messages a minute with two numbers. Enough for staff sign-ins and the pilot's order updates with push first; a new number starts at 30 a day with about 15 first contacts, so both numbers are linked at least three weeks before customer sign-ups (S16), which revisits the number count with volumes measured in S03.
- Ban thresholds and memory for several sessions in one process were not measured by Spike B; S03 records what it observes.
