# apps/api

The NestJS API (ADR 0002, ADR 0020): REST under `/api`, Express, ESM, on Node 24. Copied from Vertex Shifa's API and adapted. Modules: S01's `platform/tenancy`, `platform/areas`, `platform/files`; S02's `platform/identity` and `platform/access` (staff sessions on registered PCs and personal devices; console sessions of platform users); S03's `platform/messaging` (Vertex's WhatsApp numbers and the gateway OTP sender); S04's `platform/sync` (the restaurant PCs' command upload and sync routes). Customer and driver routes are refused with `UNAUTHENTICATED` until S16 and S19.

## Layout
- `src/main.ts` starts the process with `bodyParser: false`; `src/app.module.ts` (`AppModule.forRoot(config)`) imports the core and every module; `src/app.ts` (`configureApp`) holds what production and tests both apply, in order: no `X-Powered-By`, `trust proxy` loopback (`@Ip()` is the client's address), prefix `/api`, CORS for the exact origins of `CORS_ORIGINS` without credentials (tested in `test/cors.test.ts`), the authentication step, then the JSON (up to 1 MB: a sync upload of 100 commands) and form body parsers, shutdown hooks.
- `src/core/config/`: the environment checked by Zod at start-up (`loadConfig`: `DATABASE_APP_URL`, `API_HOST` default loopback, `API_PORT` default 3100, `CORS_ORIGINS` default `app://restaurant` plus the restaurant app's loopback dev origins outside production; `CONSOLE_ORIGINS`, the only origins console writes are accepted from (spec S02 rule 41), default the console's loopback dev origins outside production and none in production; the identity keys `IDENTITY_HASH_KEY`, `IDENTITY_ENCRYPTION_KEY`, `IDENTITY_TOKEN_KEY`, `IDENTITY_POW_DIFFICULTY`, `OTP_SENDER` (`fake` or `gateway`) and the messaging keys `MESSAGING_HASH_KEY`, `MESSAGING_ENCRYPTION_KEY` shared with the worker and the gateway, the sync keys `SYNC_TOKEN_KEY` (the sync service's tokens and the JWKS) and `SYNC_CA_ENCRYPTION_KEY` (the branch CAs' keys), `SYNC_ENDPOINT` (required in production) and `SYNC_MINIMUM_APP_VERSION` (default `0.0.0`), whose all-zero examples, the fake sender and a proof of work under 16 bits are refused in production), provided as `CONFIG`.
- `src/core/database/`: `DATABASE`, the one Drizzle database of the process, connected as the app role (`food_app`, no RLS bypass); the pool closes on shutdown. `isUniqueViolation(error, constraint)` turns a unique violation into a coded refusal; `isDeadlineExceeded(error)` (a statement or lock deadline, 57014 or 55P03) answers `SERVICE_UNAVAILABLE`, which the client may retry.
- `src/core/access/`: the route declarations (`access.decorators.ts`: `@Public`, `@StaffRoute([options,] ...permissions)` with `device: 'required'`, `reauth` and `whileClosed`, `@DeviceRoute`, `@TicketRoute`, `@ConsoleRoute`…), the authentication step (`authentication.ts`, spec S02 rule 46: Express middleware ahead of the body parser that finds the route, verifies its session, device token, ticket or console cookie through the identity module's `SessionVerifier` port, `session-verifier.ts`, and refuses before the body is read; a console request is checked whole there, origin, permission and TOTP re-entry included, and written to the platform audit refused or not), the global `AccessGuard` (fail closed; permissions, registered PC, 5-minute password or TOTP re-entry, a closed tenant's read-only access), the actors (`StaffActor`, `DeviceActor`, `Ticket`, `PlatformActor`, `SystemActor` for the CLI) with `requirePermission(actor, permission, branchId?)` and `CurrentStaff` / `CurrentDevice` / `CurrentTicket` / `CurrentPlatformUser`.
- `src/core/cookies/cookies.ts`: `@ResponseCookies()` and the `CookieWriter` interceptor, so handlers set `HttpOnly`, `Secure`, `SameSite=Strict` cookies without `@Res()`.
- `src/core/audit/audit.ts` (`audit`, `auditPlatform`) and `src/core/events/outbox.ts` (`emit`, checked against the event catalog): written in the change's transaction.
- `src/core/validation/request-validation.ts`: the global pipe that runs each route's request schemas and hands the handler the parsed value; a refusal is `VALIDATION_FAILED` with the field paths only.
- `src/core/concurrency/updated-at.ts` (`assertCurrent`, `nextUpdatedAt`: optimistic concurrency), `src/core/rate-limit/` (`RateLimiter`, in process memory), `src/core/uploads/rejected-upload.ts` (multer refusals become `FILE_REJECTED`) and `image-upload.ts` (`imageUpload(purpose)`, the one-part multipart reader of the image routes, tested over HTTP in `test/uploads.test.ts`), `src/core/serialization/contract-serializer.ts` (answers through the route's schema; files and 204 pass).
- `src/core/routes.ts` (`listRoutes`) and `src/core/openapi/openapi.ts` (`buildOpenApiDocument`): the committed `openapi.json`, which `test/openapi.test.ts` keeps current.
- `src/core/errors/error.filter.ts`: every error leaves as `{ code, message, details? }` with the status of its code (`errorStatus` in `packages/contracts`); framework errors get a fixed message; unexpected errors are logged through `describeForLog` from `@vertex-food/db`.
- `src/core/health/`: `GET /api/health`, public.
- `src/modules/<platform|food|restaurant|marketplace|dispatch>/<module>/`: one folder per module (ADR 0020 anatomy). **The pattern to copy is `modules/platform/tenancy/`**: `tenancy.module.ts`, `tenancy.controller.ts` (restaurant routes), `tenancy.console.controller.ts` (`/api/console/`), `tenancy.service.ts`, `tenancy.views.ts` (rows to contracts), `index.ts` (the public surface). Another module is reached only through its `index.ts`. A module that needs data another module owns declares a port (`tenancy/ports.ts`, `access/ports.ts`) that the owner provides from a `@Global()` module, so module imports never cycle.
- `modules/platform/identity/` (spec S02): keyed hashes and AES-GCM from `@vertex-food/crypto` under identity's own keys (`KEYED_HASH`, `SECRET_BOX`), Argon2id passwords and PIN verifiers (`secrets.ts`), EdDSA tokens (`tokens.ts`), single-use tickets bound to the account's password and server nonces (`tickets.ts`, `single-use.ts`), proof of work, OTPs behind the `OtpSender` port (sent in the challenge's transaction; `FakeOtpSender` or messaging's `GatewayOtpSender` by `OTP_SENDER`; a failed new-device delivery expires the code and starts no cooldown, spec S03 rule 19) and the public delivery route `GET /api/auth/otp/{challengeId}/delivery` (new-device codes only, 120 per 10 minutes per address), the sign-in lock and decoys, `AuthService` (sign-in, OTP, passwords, tenant options, personal sessions), `DevicesService` (registration, which calls sync's `BRANCH_PCS` port of `ports.ts`; device tokens, member lists, wipe, management), `DeviceProofs` (a challenge nonce used up for the quarantine upload), `SessionsService` (PIN sessions, refresh with reuse detection, re-auth, the `SessionVerifier`), `MeService`; the console's `ConsoleAuthService` (sign-in with password or setup code, TOTP as RFC 6238 in `totp.ts` with used steps refused, recovery codes, setup, re-auth, sessions in an `HttpOnly` cookie under `/api/console/` with 30-minute idle and 12-hour limits, the verifier of every console request and its `console.request` audit entry), `PlatformUsersService` (setup codes, console limits, no change to oneself, `LAST_ADMIN` on disable, demotion and reset with the admins locked first and the operator rechecked) and `ConsoleAccountsService` (owner recovery: lookup, password-reset authorization, phone change, audited on the platform and in each tenant the account owns). A tenant's closure ends its sessions and revokes its PCs in the closure's transaction (`device-access.ts`), and again when a verifier meets a tenant that a scheduled closure closed.
- `modules/platform/messaging/` (spec S03, ADR 0034): `MessagingService` and its console routes (`/api/console/whatsapp-sessions`, `/api/console/messaging/health`) for Vertex's platform numbers: usage counted from each number's `linked_at` as `whatsappNumberCandidates` counts it, the last 50 events, the QR opened under `whatsappQrSealContext`, add (`WHATSAPP_SESSION_LIMIT`), re-link, pause, resume and unlink, each with a session event and a platform audit entry; it never connects to WhatsApp, the gateway holding a session's lease acts on these changes. `GatewayOtpSender` checks `sendAvailability` and queues the code with `enqueueWhatsAppMessage` under the messaging keys (`MESSAGING_CRYPTO`, never identity's). Admins' names come from identity through the `PLATFORM_USER_NAMES` port (`ports.ts`); messaging imports identity's types only, so the modules never import each other at run time.
- `modules/platform/sync/` (spec S04, ADR 0022, 0035): `CommandPipeline` (`command-pipeline.ts`), `POST /api/sync/commands` from the branch's hub or standby (`DEVICE_NOT_HUB_CAPABLE` otherwise; `PROTOCOL_UNSUPPORTED` 426 before anything runs): each command in its own transaction under a lock on its id (`sync-locks.ts`), a known id answering its stored outcome (`replay`) and another version kept once per hash in `command_replays` with a `replay_mismatch` item; rule 8's checks in order, the signature through `checkEnvelope` and `ed25519Verifier` against the executor's key in the token's branch (a security log line, ids only), the executor revoked before the effective time (the quarantine), the member's access snapshot at the effective time and rule 16 (`command-access.ts`, unit-tested); an id the tenant does not hold (executor, member, approver) is answered without being stored; the executor runs in a savepoint (SYNC-01), an exception is `server_error`, a database or infrastructure failure answers 5xx; flags and attention items (`openAttention`). Executors (`executors.ts`, `defineExecutor`; `COMMAND_EXECUTORS` checked against `COMMAND_REGISTRY` at start) of `sync.network_check` and `audit.record_local_events`. `SyncDevicesService`: the sync service's token (`sync-tokens.ts`, `SYNC_TOKEN_KEY`, its JWKS at `GET /api/.well-known/jwks.json`), heartbeats and branch connectivity (`connectivity.ts`), number blocks (`number-blocks.ts`, with `numberBlocks.check` and `numberBlocks.taken` for S09's executors), PC certificates (`certificates.ts`, `@peculiar/x509`, ECDSA P-256, private IPv4 only); `UPDATE_REQUIRED` 426 below the minimum version on the token and the blocks. `BranchNetworkService` (hub roles with `HUB_ROLE_ACTIVE`, sync status), `AttentionService`, `QuarantineService` (the revoked PC's upload, signed over a device-token challenge nonce used up through identity's `DeviceProofs`, at most 10 000 of its own commands per batch, any beyond refused and audited, in uploads of up to 1 MB; the commands another PC executed run through rule 8 instead of being held; a decided batch takes nothing more, and a later command of the revoked PC is rejected `device_revoked`; accept and reject with re-auth; accepted commands run in journal order without the device check, each in its own transaction, and an accept cut short is finished by accepting again). A known id of another branch is answered `signature_invalid` without being read or stored. It provides identity's `BRANCH_PCS` (`branch-pcs.ts`: the first two PCs of a branch take the hub and standby roles; the branch CA is made with the first, its key sealed under `sync.branch-ca:<tenant>:<authority>`).
- `modules/platform/access/` (spec S02): memberships (`memberships.ts`), `StaffService` (rule 7 on every write, `LAST_OWNER` with the owners locked first), the first owner of a new tenant (`TENANT_OWNERS`), and no branch archived while it is an active member's only one (`TENANT_MEMBERS`, `BRANCH_HAS_MEMBERS`).
- `src/cli/`: `main.ts` and `commands.ts`, the CLI for Vertex staff on the server (`pnpm --filter @vertex-food/api cli <command> --operator <name> …`, after `build`; an unknown command prints the usage; `tenant:create` takes the first owner, `--owner-phone` and `--owner-name`; `platform-user:create` and `platform-user:reset` print a one-time setup code, `account:authorize-password-reset` and `account:change-phone` recover an owner, spec S02 rule 15). Each command calls the service of its console route as the `system` actor with the operator's name. The area commands (`governorate:add`, `city:add`) open `DATABASE_OWNER_URL`, because the app role only reads areas.
- `test/`: integration tests against a fresh migrated database per run (`test/global-setup.ts`, `createTestApp` in `test/app.ts` with identity keys made per run and a 4-bit proof of work); `createTestApp({ otpSender: 'gateway' })` runs the gateway sender with messaging keys made per run (`TEST_MESSAGING_ENV`, so `test/messaging.test.ts` opens the queued codes); `test/console.ts` gives console users signed in over HTTP with their TOTP re-entry; `test/staff.ts` gives real sessions over HTTP (`TestApi.ownerOnDevice()`, `TestDevice.addMember`, `signIn`, `as(session)`), from random client addresses so per-address limits stay per test, and files that send two OTPs to one phone run with a fake `Date` (`vi.useFakeTimers({ toFake: ['Date'], shouldAdvanceTime: true })`); `createTestApp({ env, overrides })` adds environment and replaces providers (a command registry with test commands in `test/sync-rollback.test.ts`); `test/sync.ts` signs commands with a test PC's key (`signedCommand`, `resign`), uploads them and registers the branch's other PCs (`registerPc`), and `test/sync-*.test.ts` cover the sync routes; `test/sync-service.test.ts` (only with `SYNC_SCENARIOS=1`, `packages/sync/CLAUDE.md`) starts the sync service in Docker on the run's database and reads each PC's streams over PowerSync's HTTP protocol; `test/architecture/` holds the rules of ADR 0020 and their proofs on broken examples. Unit tests sit next to the code (`*.test.ts`).

## Rules
- Every route declares its response schema with `@SerializeOptions({ schema })`, a contract schema with `.meta({ id })` (`noContentSchema` for 204, `fileBytesSchema` for a file); its access (`@Public()`, `@CustomerRoute()`, `@DriverRoute(fleet)`, `@StaffRoute([options,] ...permissions)`, `@DeviceRoute()`, `@TicketRoute(purpose)`, `@ConsoleRoute([options,] ...permissions)` with `reauth` and `subjectTenant` (the parameter naming the tenant, for the platform audit); console routes only under `/api/console/`, where only the sign-in steps under `/api/console/auth/` are public) and its entitlement (`@RequiresFeature(key)` or `@NoFeature()`). Handlers never take `@Res()` or `@Next()`. The architecture test enforces all of it.
- Services check permissions too (`requirePermission`), with the branch of the resource for branch-scoped staff; a route's `@StaffRoute` admits a member holding any of its permissions.
- Injection is always explicit: `constructor(@Inject(TOKEN) private readonly x: X)`. No decorator metadata is emitted (`@vertex-food/config/tsconfig/nest.json`), so an implicit parameter would be `undefined`.
- Tenant data only inside `withTenant(db, tenantId, tx => …)` from `@vertex-food/db`, with the tenant from the session or device, never from the request body or query (ADR 0004); a sign-in ticket's choice of tenant is the one exception, rechecked under that tenant's RLS. Platform tables without RLS (`tenants`, `tenant_slugs`, `governorates`, `cities`, `accounts` and the other identity tables, `account_tenant_links`, the `whatsapp_*` tables of messaging) are imported only by their module (architecture test).
- Secrets: passwords and PINs as Argon2id, codes and tokens as keyed hashes, secrets read back sealed (ADR 0032); never a phone, a code, a token or a password in a log, an error message or an audit entry (ids only).
- Every change writes its audit entry and outbox event in its transaction; edits carry the `updatedAt` the client read (`CONFLICT` when stale).
- A business refusal throws `DomainError(code, message, details?)` from `@vertex-food/contracts`; the message is English, for logs, and carries ids at most; `details` holds ids, codes and times. Never log request bodies, query parameters, a phone, a customer's address, a driver's location or a database error's message: use `describeForLog` (ADR 0016).
- Totals, prices and attribution are computed by the server, never trusted from a client (ADR 0006, 0007).
- A route or contract change regenerates `openapi.json`: `pnpm --filter @vertex-food/api exec vitest run test/openapi.test.ts -u`, then review the diff.

Run: `pnpm --filter @vertex-food/api test` (needs the local database, `packages/db/CLAUDE.md`) · start (after `build`): `pnpm --filter @vertex-food/api start` · CLI: `pnpm --filter @vertex-food/api cli …`.
