# apps/api

The NestJS API (ADR 0002, ADR 0020): REST under `/api`, Express, ESM, on Node 24. Copied from Vertex Shifa's API and adapted. Modules: S01's `platform/tenancy`, `platform/areas`, `platform/files`; S02's `platform/identity` and `platform/access` (staff sessions on registered PCs and personal devices). Console sessions arrive with S02's console identity: until then console routes are refused with `UNAUTHENTICATED`, as customer and driver routes are until S16 and S19.

## Layout
- `src/main.ts` starts the process with `bodyParser: false`; `src/app.module.ts` (`AppModule.forRoot(config)`) imports the core and every module; `src/app.ts` (`configureApp`) holds what production and tests both apply, in order: prefix `/api`, no `X-Powered-By`, `trust proxy` loopback (`@Ip()` is the client's address), CORS for the exact origins of `CORS_ORIGINS` without credentials (tested in `test/cors.test.ts`), the authentication step, then the JSON and form body parsers, shutdown hooks.
- `src/core/config/`: the environment checked by Zod at start-up (`loadConfig`: `DATABASE_APP_URL`, `API_HOST` default loopback, `API_PORT` default 3100, `CORS_ORIGINS` default `app://restaurant` plus the restaurant app's loopback dev origins outside production; the identity keys `IDENTITY_HASH_KEY`, `IDENTITY_ENCRYPTION_KEY`, `IDENTITY_TOKEN_KEY`, `IDENTITY_POW_DIFFICULTY` and `OTP_SENDER`, whose all-zero examples, the fake sender and a proof of work under 16 bits are refused in production), provided as `CONFIG`.
- `src/core/database/`: `DATABASE`, the one Drizzle database of the process, connected as the app role (`food_app`, no RLS bypass); the pool closes on shutdown. `isUniqueViolation(error, constraint)` turns a unique violation into a coded refusal; `isDeadlineExceeded(error)` (a statement or lock deadline, 57014 or 55P03) answers `SERVICE_UNAVAILABLE`, which the client may retry.
- `src/core/access/`: the route declarations (`access.decorators.ts`: `@Public`, `@StaffRoute([options,] ...permissions)` with `device: 'required'`, `reauth` and `whileClosed`, `@DeviceRoute`, `@TicketRoute`, `@ConsoleRoute`…), the authentication step (`authentication.ts`, spec S02 rule 46: Express middleware ahead of the body parser that finds the route, verifies its session, device token or ticket through the identity module's `SessionVerifier` port, `session-verifier.ts`, and refuses before the body is read), the global `AccessGuard` (fail closed; permissions, registered PC, 5-minute password re-entry, a closed tenant's read-only access), the actors (`StaffActor`, `DeviceActor`, `Ticket`, `PlatformActor`, `SystemActor` for the CLI) with `requirePermission(actor, permission, branchId?)` and `CurrentStaff` / `CurrentDevice` / `CurrentTicket` / `CurrentPlatformUser`.
- `src/core/cookies/cookies.ts`: `@ResponseCookies()` and the `CookieWriter` interceptor, so handlers set `HttpOnly`, `Secure`, `SameSite=Strict` cookies without `@Res()`.
- `src/core/audit/audit.ts` (`audit`, `auditPlatform`) and `src/core/events/outbox.ts` (`emit`, checked against the event catalog): written in the change's transaction.
- `src/core/validation/request-validation.ts`: the global pipe that runs each route's request schemas and hands the handler the parsed value; a refusal is `VALIDATION_FAILED` with the field paths only.
- `src/core/concurrency/updated-at.ts` (`assertCurrent`, `nextUpdatedAt`: optimistic concurrency), `src/core/rate-limit/` (`RateLimiter`, in process memory), `src/core/uploads/rejected-upload.ts` (multer refusals become `FILE_REJECTED`) and `image-upload.ts` (`imageUpload(purpose)`, the one-part multipart reader of the image routes, tested over HTTP in `test/uploads.test.ts`), `src/core/serialization/contract-serializer.ts` (answers through the route's schema; files and 204 pass).
- `src/core/routes.ts` (`listRoutes`) and `src/core/openapi/openapi.ts` (`buildOpenApiDocument`): the committed `openapi.json`, which `test/openapi.test.ts` keeps current.
- `src/core/errors/error.filter.ts`: every error leaves as `{ code, message, details? }` with the status of its code (`errorStatus` in `packages/contracts`); framework errors get a fixed message; unexpected errors are logged through `describeForLog` from `@vertex-food/db`.
- `src/core/health/`: `GET /api/health`, public.
- `src/modules/<platform|food|restaurant|marketplace|dispatch>/<module>/`: one folder per module (ADR 0020 anatomy). **The pattern to copy is `modules/platform/tenancy/`**: `tenancy.module.ts`, `tenancy.controller.ts` (restaurant routes), `tenancy.console.controller.ts` (`/api/console/`), `tenancy.service.ts`, `tenancy.views.ts` (rows to contracts), `index.ts` (the public surface). Another module is reached only through its `index.ts`. A module that needs data another module owns declares a port (`tenancy/ports.ts`, `access/ports.ts`) that the owner provides from a `@Global()` module, so module imports never cycle.
- `modules/platform/identity/` (spec S02): keyed hashes and AES-GCM (`crypto.ts`), Argon2id passwords and PIN verifiers (`secrets.ts`), EdDSA tokens and the JWKS (`tokens.ts`), single-use tickets and server nonces (`tickets.ts`, `single-use.ts`), proof of work, OTPs behind the `OtpSender` port with `FakeOtpSender` until S03, the sign-in lock and decoys, `AuthService` (sign-in, OTP, passwords, tenant options, personal sessions), `DevicesService` (registration, device tokens, member lists, wipe, management), `SessionsService` (PIN sessions, refresh with reuse detection, re-auth, the `SessionVerifier`), `MeService`. A tenant's closure ends its sessions and revokes its PCs in the closure's transaction (`device-access.ts`), and again when a verifier meets a tenant that a scheduled closure closed.
- `modules/platform/access/` (spec S02): memberships (`memberships.ts`), `StaffService` (rule 7 on every write, `LAST_OWNER` with the owners locked first), the first owner of a new tenant (`TENANT_OWNERS`).
- `src/cli/`: `main.ts` and `commands.ts`, the CLI for Vertex staff on the server (`pnpm --filter @vertex-food/api cli <command> --operator <name> …`, after `build`; an unknown command prints the usage; `tenant:create` takes the first owner, `--owner-phone` and `--owner-name`). Each command calls the service of its console route as the `system` actor with the operator's name. The area commands (`governorate:add`, `city:add`) open `DATABASE_OWNER_URL`, because the app role only reads areas.
- `test/`: integration tests against a fresh migrated database per run (`test/global-setup.ts`, `createTestApp` in `test/app.ts` with identity keys made per run and a 4-bit proof of work); `test/staff.ts` gives real sessions over HTTP (`TestApi.ownerOnDevice()`, `TestDevice.addMember`, `signIn`, `as(session)`), from random client addresses so per-address limits stay per test, and files that send two OTPs to one phone run with a fake `Date` (`vi.useFakeTimers({ toFake: ['Date'], shouldAdvanceTime: true })`); `test/architecture/` holds the rules of ADR 0020 and their proofs on broken examples. Unit tests sit next to the code (`*.test.ts`).

## Rules
- Every route declares its response schema with `@SerializeOptions({ schema })`, a contract schema with `.meta({ id })` (`noContentSchema` for 204, `fileBytesSchema` for a file); its access (`@Public()`, `@CustomerRoute()`, `@DriverRoute(fleet)`, `@StaffRoute([options,] ...permissions)`, `@DeviceRoute()`, `@TicketRoute(purpose)`, `@ConsoleRoute(permission)`, console routes only under `/api/console/`) and its entitlement (`@RequiresFeature(key)` or `@NoFeature()`). Handlers never take `@Res()` or `@Next()`. The architecture test enforces all of it.
- Services check permissions too (`requirePermission`), with the branch of the resource for branch-scoped staff; a route's `@StaffRoute` admits a member holding any of its permissions.
- Injection is always explicit: `constructor(@Inject(TOKEN) private readonly x: X)`. No decorator metadata is emitted (`@vertex-food/config/tsconfig/nest.json`), so an implicit parameter would be `undefined`.
- Tenant data only inside `withTenant(db, tenantId, tx => …)` from `@vertex-food/db`, with the tenant from the session or device, never from the request body or query (ADR 0004); a sign-in ticket's choice of tenant is the one exception, rechecked under that tenant's RLS. Platform tables without RLS (`tenants`, `tenant_slugs`, `governorates`, `cities`, `accounts` and the other identity tables, `account_tenant_links`) are imported only by their module (architecture test).
- Secrets: passwords and PINs as Argon2id, codes and tokens as keyed hashes, secrets read back sealed (ADR 0032); never a phone, a code, a token or a password in a log, an error message or an audit entry (ids only).
- Every change writes its audit entry and outbox event in its transaction; edits carry the `updatedAt` the client read (`CONFLICT` when stale).
- A business refusal throws `DomainError(code, message, details?)` from `@vertex-food/contracts`; the message is English, for logs, and carries ids at most; `details` holds ids, codes and times. Never log request bodies, query parameters, a phone, a customer's address, a driver's location or a database error's message: use `describeForLog` (ADR 0016).
- Totals, prices and attribution are computed by the server, never trusted from a client (ADR 0006, 0007).
- A route or contract change regenerates `openapi.json`: `pnpm --filter @vertex-food/api exec vitest run test/openapi.test.ts -u`, then review the diff.

Run: `pnpm --filter @vertex-food/api test` (needs the local database, `packages/db/CLAUDE.md`) · start (after `build`): `pnpm --filter @vertex-food/api start` · CLI: `pnpm --filter @vertex-food/api cli …`.
