# apps/restaurant

Vertex Food Restaurant, the offline-first Windows app (ADR 0008, 0022, 0023, layout ADR 0020): a React + Vite + TanStack Router renderer in an Electron shell, Arabic-first RTL (ADR 0018). Copied from Vertex Shifa's clinic skeleton and adapted. Today it has the shell, S01's online-only setup screens and S02's identity of the PC (registration, member list, PIN sessions online and offline) with its preload API, and S02's back office (staff, devices, branch security, My account, personal-device mode): no local database, sync client, branch hub, printing or packaging yet (S04, S10 and S11 bring them).

## Layout
- `src/main.tsx` mounts i18n, the `DirectionProvider` and the router; `src/routes/` holds thin file-based routes (TanStack Router; `src/routeTree.gen.ts` is generated by the Vite plugin on `dev` and `build`, committed, never edited or read); `__root.tsx` sets the shell and the error and not-found states.
- `src/features/<area>/`: the components, queries and forms of one area. The pattern to copy for an online-only screen is S01's: `features/tenancy/` (`queries.ts` with `queryOptions`, the API calls and `useSetupCache`; pure drafts and checks with unit tests in `branch-draft.ts`; shared fields), `features/settings/` (a form per section: `useDraft`, `useSettingsSave`, `SaveActions`, the `updatedAt` it started from kept as its base), `features/setup/` (the wizard). `tenant-gate.tsx` wraps every route (`__root.tsx`): tenant loaded first, onboarding redirects, status banner, offline notice. App-wide `src/components/` (shell, state card, `QueryStates`, `OfflineNotice`, `FieldGroup`) and `src/lib/`: `i18n.ts`; `error-logging.ts` (errors logged by name only); `api.ts` (`openapi-fetch` client typed by `api-schema.gen.ts`, `unwrap` to `ApiError` with the code only); `query-client.ts` (nothing paused or queued offline, `fetchNow`); `online.ts`; `error-text.ts` (the Arabic text of a code); `format.ts`; `staff-access.ts` (`useStaffAccess`, `can`: the session's access, provided by the session gate); `device.ts` (`deviceBridge`: the preload's `window.vertexDevice`, null in a browser). `features/session/` (spec S02): `session-gate.tsx` is the root route's component: on a registered PC it follows the main process's status (welcome, the lock screen, the choose-PIN dialog for a member without a PIN, the wipe notice, the idle lock and "Switch cashier"), in a browser the personal session of `GET /api/me`; then the shell, `TenantGate` and the screen. The PIN pad, member picker, approval and re-enable dialogs and the offline-window warnings live there; `features/sign-in/` holds the sign-in flow (proof of work, OTP, first password), the registration of the PC and the browser's tenant choice; the `signed_in` ticket stays in memory (`ticket.ts`). `features/session/reauth.tsx` is the password dialog of sensitive actions (rule 26): `useSensitive()(action)` runs the action again after `REAUTH_REQUIRED`, and a closed dialog throws `ReauthCancelled`; `forgot-pin-dialog.tsx` lets an owner or manager replace a forgotten PIN by password on the lock screen (rule 22, through the bridge's `signInByPassword`); `personal-actions.tsx` holds the personal-device shell's sign-out and tenant switcher; `useMe()` gives the screens the session's `GET /api/me`. `features/staff/` (screens 9, 10): `access-draft.ts` (roles, branches and the owner's adjustments as pure, tested rules), `access-fields.tsx`, the list, add-member (with the PIN handover on a PC) and member screens, and `queries.ts` with the staff, device and My account calls; `features/devices/` (screen 11) and `features/account/` (screen 13); branch security (screen 12) is a section of `settings/branch-sections.tsx`.
- The UI comes from `packages/ui` (ADR 0018): `src/styles.css` imports Tailwind, `fonts-desktop.css` and the design system's styles; `vite.config.ts` adds `vertexFoodWeb()` (`theme-init.js` before the first paint, the first screen's fonts preloaded, both served from `'self'` under the CSP). The shell (`components/app-shell.tsx`) is `AppLayout`: the sidebar with the links of `features/tenancy/restaurant-nav.tsx` (none while the tenant loads, in the wizard or "setup in progress"), the `ThemeToggle` and `PoweredBy`; `index.html` takes the favicon from `brand/`.
- `electron/main.ts`: the main process. It owns the PC's identity (spec S02): `device-service.ts` (registration, device tokens by a signed server nonce, the member list every 60 seconds and its confirmation, PIN sessions online through the API and offline in `local-pins.ts` against the Argon2id verifiers with `hash-wasm`, because Electron's BoringSSL has no Argon2; the local lockout, approvals, the offline window and the highest-seen clock; the wipe of a revoked PC; an owner's or manager's session by password with the device token, to replace a forgotten PIN), `device-store.ts` (one record sealed by `safeStorage` in the user's data folder: the Ed25519 key of `device-key.ts` and the member list), `device-client.ts` (the device routes of the API, whose origin comes from the build's `connect-origins.json`, or `VITE_API_URL` in the environment for `dev:electron` before a build). The renderer reaches it only through `preload.cts` (sandboxed, so CommonJS requiring nothing but `electron`) and the IPC API of `bridge.ts`, whose handlers (`device-ipc.ts`) parse every input and answer only the app's own frame; no verifier, key, device token or refresh token crosses it, only the online session's access token. One window (`electron/window-options.ts`: shrinks to 360 × 480, so the phone layout applies to a narrow window too) with `contextIsolation`, `sandbox`, no `nodeIntegration`; the preload above; new windows, webviews and navigation outside the renderer's origin refused; every permission denied; one instance only. The built renderer is served from `app://restaurant/` (`electron/app-protocol.ts`: path containment, client routes get `index.html`, a strict CSP header). `--dev-server=<url>` loads the Vite dev server, only when unpackaged and only on loopback HTTP (`electron/navigation.ts`). The local database, the sync client, the hub server (ADR 0022) and printing (ADR 0023) join the main process here.
- `hub-clients/` (not created yet; kitchen display and waiter app, ADR 0008, 0022): the web clients the hub serves over the LAN, added by S04 (the hub), S11 (the kitchen display) and S12 (the waiter app).
- `src/lib/api-schema.gen.ts` is generated from `apps/api/openapi.json` by `test/api-schema.test.ts`; after an API change run `pnpm --filter @vertex-food/restaurant exec vitest run test/api-schema.test.ts -u`. Never edit or read it.
- Configuration, read at build by Vite: `VITE_API_URL` (the API's URL; unset, requests go to the renderer's own origin, which only the E2E uses). The build writes its origin (`connectOrigins` in `electron/app-protocol.ts`: HTTPS or loopback HTTP only) to `dist/renderer/connect-origins.json`, which the main process and `vite preview` read for `connect-src`, so the policy always names the API the renderer was built with.
- Unit tests sit next to the code; the logical-CSS and token rules are `packages/ui`'s convention test, which covers `src/`. `e2e/`: Playwright against `vite preview` (Chromium, Electron's engine), light and dark, with Electron's CSP header (`vite.config.ts` reads it from `electron/app-protocol.ts`); any CSP violation fails the test (`failOnCspViolation`). `e2e/mock-api.ts` answers the API's routes in memory with the contracts' schemas and rules (stale `updatedAt`, suspended and closed writes, a due scheduled change through `effectiveStatusState` at its `clock`, which a `page.clock` test points at the page's, completeness) and the sign-in steps of S02 with the browser's personal session (the owner's by default, `me: null` for signed out), the staff, device, branch-security and My account routes, and the password re-entry of sensitive routes (`reauthenticated`); `e2e/fake-device.ts` stands in for the main process (`window.vertexDevice` installed before the page loads, with the rules of `local-pins.ts`), so the E2E covers a registered PC in Chromium; synthetic data only.
- Ports: dev 5273, `vite preview` 4273 (console 5274/4274, web 5275/4275), so every E2E server runs side by side; the range differs from Vertex Shifa's (51xx/41xx) so both projects run on one PC.

## Rules
- Every text through i18next with keys from `packages/i18n` (`useTranslation('<namespace>')`; this app's namespace is `restaurant`); never a literal in a component. Numbers and dates through `Intl` with `formatLocale` from `@vertex-food/i18n` (Syrian month names, Latin digits); times shown in `displayTimeZone` (`Asia/Damascus`).
- Design-system components and tokens only (`packages/ui`): semantic utilities (`bg-surface`, `text-muted-foreground`), never a color value, logical directions only (`ms-`, `ps-`, `start-`, `text-start`): pinned by `packages/ui/src/conventions.test.ts`. The window title comes from i18n too (`document.title`).
- Every screen has its loading, empty, error and offline states (ADR 0020); once sync exists, the sync status and last sync time are always visible (ADR 0008). An error state never shows or logs the error's message: it may carry customer data (ADR 0016). `main.tsx` routes React's and the router's error hooks to `logErrorLabel` and redacts any `Error` passed to `console.error`/`console.warn`; log errors with `logErrorLabel`, never the error object or its message.
- The renderer is untrusted: it gets no Node access. The local database, sync and the hub live in the main process; the renderer reaches them only through the preload's narrow IPC API (`bridge.ts`), which never carries a secret the renderer does not need. Never loosen `contextIsolation`, `sandbox` or the CSP; a new origin (API, sync service) is added to `connect-src` explicitly.
- Data comes from the local database and changes go through sync commands sent to the active hub (ADR 0008, 0022). Configuration screens (S01) are online only: they call the API through `src/lib/api.ts` and TanStack Query, never queue a change, and while offline keep the last loaded values read-only (`OfflineNotice`) or show `OfflineState`. Every edit sends the `updatedAt` it started from; a `CONFLICT` reloads the record and says so.
- `main.tsx` mounts `CSPProvider disableStyleElements`: Base UI may not inject `<style>` under the CSP; the rules it would inject live in `packages/ui`'s `base.css`.
- "Powered by Vertex Food" (`PoweredBy`) is always visible (ADR 0018). The restaurant's accent (`tenantStyle`, `bg-tenant-accent`) arrives with branding (S08); the rest keeps the Vertex identity (ADR 0010).
- UI changes add or update the E2E RTL screenshots (light and dark) and are looked at before the PR. Every screen is in `e2e/responsive.spec.ts` at the `viewports` of `e2e/screenshot.ts` (phone, tablet both ways, desktop), with `expectNoHorizontalOverflow` and, below 1024 px, 44 px touch targets (`e2e/screenshot.ts`).

Run: `pnpm --filter @vertex-food/restaurant test` · E2E: `pnpm verify apps/restaurant/e2e/<file>.spec.ts` (builds first; `pnpm verify` runs the whole suite when the branch affects this app, and CI runs every suite, `docs/testing.md`) · dev: `pnpm --filter @vertex-food/restaurant dev` (browser) and `pnpm --filter @vertex-food/restaurant dev:electron` (Electron on the dev server) · built app: `pnpm --filter @vertex-food/restaurant start`.
