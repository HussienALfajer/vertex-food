# apps/whatsapp-gateway

The WhatsApp gateway (ADR 0012, ADR 0034, spec S03, layout ADR 0020): a long-running NestJS process, ESM, Node 24, that runs Vertex's platform numbers and sends the `whatsapp_messages` queue. Adapted from Vertex Shifa's gateway and its Spike B. It talks to the API and the worker only through the database (no HTTP between them), and keeps a loopback `GET /health` for the process manager.

## Layout
- `src/main.ts` starts the process; `src/gateway.module.ts` (`GatewayModule.forRoot(config, { runLoops })`) wires everything; `src/app.ts` (`configureApp`) holds what production and tests both apply; `src/loops.ts` runs the timers (lease tick 10 s, claim poll 2 s plus `LISTEN whatsapp_messages`, sweep 60 s). Not pg-boss.
- `src/core/config/`: the environment checked by Zod (`loadConfig`): `GATEWAY_HOST`/`GATEWAY_PORT` (loopback, 3102), `DATABASE_APP_URL` (must be `food_app`), `MESSAGING_HASH_KEY`, `MESSAGING_ENCRYPTION_KEY` (32 bytes base64, shared with the API and the worker), `WHATSAPP_TRANSPORT` (`fake` or `baileys`); production refuses `fake` and the all-zero example keys. `src/core/database/`: `DATABASE` and `MESSAGING_CRYPTO` (`KeyedHash`, `SecretBox` from `@vertex-food/crypto`). `src/core/log/describe-error.ts`: errors by name or SQLSTATE only. `src/core/tasks.ts`: fire-and-forget work, logged on failure, awaited by tests and shutdown.
- `src/transport/`: `WhatsAppTransport` (`whatsapp-transport.ts`), the only seam to WhatsApp: `connect(sessionId, credentials, events)` → `sendText`, `logout`, `close`; events `qr`, `open`, `close` (library-neutral reason), `message`, `receipt`, and the caller's `sentText` lookup for retry requests. `FakeWhatsAppTransport` sends nothing and lets tests drive scans, disconnects, messages, receipts, retry requests and failures. `BaileysWhatsAppTransport` (exact `baileys` version pinned in `package.json`, `Browsers.ubuntu` = `WEB_BROWSER`, history and presence off, silent logger), `baileys-auth-state.ts` (Baileys' creds and key store over a `CredentialStore`), `baileys-mapping.ts` (codes, JIDs, receipts, incoming messages; unit-tested with synthetic payloads).
- `src/sessions/`: `SessionsService` (the lease: take free or expired runnable sessions, renew, close on a lost renewal, log out an unlinked one, restart a re-linked one, link timeout; QR sealed with `whatsappQrContext`; first `open` with phone and `linked_at`, duplicate numbers; the disconnect table of `session-state.ts`), `DatabaseCredentialStore` (sealed, fenced), `SessionRegistry` (connected connections, read by sending), `GATEWAY_INSTANCE` (the lease holder id).
- `src/sending/`: `SendingService` (claim, render, send, outcome, receipts, `sentText`), `render.ts` (template text from `packages/i18n` `ar.messaging`), `message-status.ts` (`endMessages`: failed or expired, with the OTP challenge), `queue-listener.ts` (`LISTEN`).
- `src/incoming/`: keywords, opt-out and the daily auto-reply. `src/alerts/`: admin alerts and the healthy count. `src/sweep/`: retention and expiry.
- `test/`: the gateway booted on a throwaway database (`global-setup.ts`) with the fake transport and its loops off (`gateway.ts`: `startGateway`, `tick`, `drain`, `settle`, the recorded `logs`); `fixtures.ts` writes what the API would (sessions, re-link, unlink, OTP challenges, platform users) as the owner role and resets the messaging tables before each test; `credentials.ts` holds the synthetic `+999` numbers. Files run one at a time (`fileParallelism: false`): a gateway takes every free session of the database. Unit tests sit next to the code.

## Rules
- Only `src/transport/` imports Baileys or a concrete transport; everything else uses the interface and `@Inject(WHATSAPP_TRANSPORT)` (`test/transport-boundary.test.ts`).
- One live connection per session: connect only while holding the lease; every state write is conditional on `lease_holder` (`held`). A failed renewal closes the connection at once; a `440` is let go and never taken again by that instance. `515` reconnects at once once; a lost connection backs off 1 s doubling to 60 s.
- What the API does and the gateway notices on its next tick (shared note with PR 3): create and re-link set `linking` with a new `link_deadline_at` (the link epoch fencing credential writes), re-link deletes credentials; unlink archives the session (`state = 'unlinked'`), keeps its lease, deletes credentials, known recipients and queued messages except OTPs, which go back to `session_id` null. The gateway logs out an unlinked session it was running and then clears the lease. A conditional state write that matches nothing means the stored session moved on: `abandon` logs out or closes and frees the lease at once.
- A renewal that fails closes every connection at once; the instance takes its own leases again once renewals work. A send that takes over 75 s (past Baileys' 60 s) is a transport error. A phone without WhatsApp (`RecipientUnreachableError`) fails the message at once, with no retry and nothing counted against the number. Within one claim a person gets one message; a message waits for the busy number that knows the person rather than spend another number's first contacts.
- Values are sealed with their contexts: QR `whatsapp-qr:<session id>` (opened by the API), credentials `whatsapp-credentials:<session id>:<key hash>`, messages `whatsappSealContext` from `@vertex-food/db`. Queue through `enqueueWhatsAppMessage`; check budgets with `sendAvailability` / `whatsappNumberCandidates`; never count sends any other way. SQL that compares a timestamp read back through a JavaScript `Date` truncates to milliseconds.
- Counts and deadlines use the database's `now()`. Rows are read unlocked and locked with `FOR UPDATE SKIP LOCKED` only when claimed, so instances do not starve each other.
- Opt-out (rule 27) stops alerts, auto-replies and notifications at claim time; OTPs and opt-out confirmations always go. Replies go only from the receiving number and only when it has budget now.
- Never log a message body, a phone, a parameter (an alert's label included), a code or a QR: logs hold session and message ids, kinds and reason codes (`test/logs.test.ts`). Library errors are logged by name only (`describeError`). Baileys gets a silent logger.
- Tests never connect to WhatsApp and never send a real message; synthetic `+999` numbers only. Baileys is exercised through its mapping and auth-state units only. An upgrade of `baileys` is tested on a test number first (ADR 0034).
- Injection is always explicit, `@Inject(TOKEN)`, as in `apps/api`.

Run: `pnpm --filter @vertex-food/whatsapp-gateway test` · start (after `build`): `pnpm --filter @vertex-food/whatsapp-gateway start`.
